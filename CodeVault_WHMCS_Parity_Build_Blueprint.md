# CodeVault 1.2 — Full WHMCS-Parity Platform (Cloned + Enhanced) — Vanilla PHP Build Blueprint

*Parity baseline: WHMCS 9.0.x (v9.0.6, Jul 2026) + 8.13 LTS. Everything WHMCS does, rebuilt in vanilla PHP, then enhanced. Stack: PHP 8.2/8.3 · PDO(mysqlnd)/MySQLi · MariaDB · Redis · libsodium+Argon2id · ionCube 13.0.2+ (optional later hardening — see §5) · MaxMind DB · GD2 · OPcache. Tooling: Claude Code + Antigravity parallel agents.*

---

## 0. Does the previous plan cover all of WHMCS? — No, and here's the gap

The earlier plan was **CMS/blog/ecommerce first**, with WHMCS's real engines (billing, provisioning, domains, support automation, module/hook SDK) sitting in an *optional* Phase 8. That is **not** full parity.

**This document supersedes that scope.** It treats **full WHMCS feature parity as the product**, folds your doc-2 requirements (licensed installer, BruteGuard, SEO/AI visibility, async email) in as **enhancements**, and enforces **one unified design system** across every page.

> Honest framing up front: WHMCS is ~15 years of engineering. A faithful clone is a large, multi-release build — the *pages* are ~30% of it; the **billing/provisioning/domain/support engines and the module+hook SDK are the other 70%**, and that's where the real time goes. This plan is structured so you (solo + agents) can ship it in **sequenced releases** that are each usable, rather than one impossible monolith. I'll be realistic about effort in §9.

**No local WHMCS reference install exists.** This is a standalone project (its own folder, own codebase, own DB — not built on top of CodeVault or any other existing product). There is no live WHMCS instance on disk to diff against or reverse-engineer; parity is built from documented/known WHMCS behavior (feature set, workflows, data shapes, edge cases), not from copying or reading any proprietary WHMCS source. Keep that in mind for later "verify against WHMCS" tasks — they mean spec/behavior comparison against documented rules, not a live-instance diff. See the **Testing & parity-verification strategy** in §7 for how billing/tax correctness gets validated without an oracle to compare against.

## 1. "Cloned + Enhanced" — the enhancement philosophy

Every module reaches **WHMCS parity first**, then adds a defined enhancement. The enhancements aren't scattered — they follow five themes, applied everywhere:

| Theme | What it means vs stock WHMCS |
|-------|------------------------------|
| **E1 · Security-first** | cPHulk/Imunify-grade BruteGuard, Argon2id/libsodium, per-country rules, firewall sync, CSRF/CSP everywhere — WHMCS's security is basic by comparison. |
| **E2 · Performance/scale** | Redis sessions+cache+queue, WebP pipeline, OPcache tuning, 100/100 Lighthouse target, horizontal-scale ready. |
| **E3 · SEO/AI visibility** | Full JSON-LD (Article/Breadcrumb/Product/Org), canonical, sitemap automation, AI-search-visibility scoring — WHMCS has almost none of this natively. |
| **E4 · Built-in AI** | DeepSeek/Claude assistant across admin + support (ticket drafting, PII redaction, KB search, fraud triage) — WHMCS only previews this in 9.0. |
| **E5 · Modern DX/UX** | One design system, cleaner module SDK, first-class API, async everything. |

Each module below is tagged with the enhancement themes it carries.

## 2. Unified Design System ("same design throughout")

Non-negotiable per your ask — one visual + interaction language across installer, client area, cart, and admin.

- **Design tokens** — a single source (colors, spacing, type scale, radii, shadows) in CSS custom properties; both themes consume the same tokens.
- **Component library** — buttons, forms, tables, cards, modals, tabs, toasts, badges (incl. the green **King** whitelist badge), data-tables with search/sort/paginate — built once, reused everywhere.
- **Two skins, one system** — Admin theme + Client/Cart theme share the component library and tokens; only layout/density differ.
- **Favicon from Site Title** — first letter of the admin-set title rendered to SVG+PNG, regenerated on title change.
- **Templating** — plain PHP view layer with escaping helpers + partials (Smarty-compatible layer optional later for third-party template portability).
- **Accessibility + responsive** baked into the component library, not bolted on.

Everything built after Phase 0 *must* use these components — no one-off markup. That's how "same design throughout" is enforced structurally, not by discipline alone.

## 3. Core architecture + the two systems that make it WHMCS

Vanilla, but the **module system and hook system are first-class** — they're what made WHMCS a platform rather than an app.

**Core kernel**
- Front controller, Router, Request/Response, DB (PDO), Config, View, Container, Session (Redis).
- **Cron scheduler** — the single system cron that drives every automated job (invoicing, suspensions, domain sync, card capture, ticket import, reminders, pruning).
- **Queue/worker** — Redis-backed async for email, provisioning calls, webhooks, heavy jobs.

**Module SDK** (parity with WHMCS's extensibility — build these interfaces early so everything plugs in):
- `ProvisioningModule` (server modules: cPanel/Plesk/DirectAdmin/CyberPanel/Virtualizor/SolusVM/Proxmox, plus real upstream-vendor VPS/dedicated APIs — InterServer VPS (`https://my.interserver.net/apiv2`) and Nocix Dedicated Server (`https://my.nocix.net/api`) — for hosting companies that resell capacity on those platforms rather than running their own hypervisor stack…)
- `RegistrarModule` (domain registrars)
- `GatewayModule` (payment gateways — merchant/tokenized + third-party/redirect)
- `AddonModule`, `ReportModule`, `NotificationModule`, `WidgetModule`, `SecurityQuestionModule`, `FraudModule`
- Each is a defined contract (create/suspend/terminate, register/transfer/renew, capture/refund, score/hold, etc.). `FraudModule` is new versus the earlier draft — the Fraud engine in §4.4 needs a matching SDK interface like every other engine has, so third-party/custom fraud scoring plugs in the same way gateways and registrars do.

**Hook system** — action-hook dispatcher with hundreds of named hook points (`ClientAdd`, `InvoicePaid`, `AfterModuleCreate`, `DailyCronJob`, `TicketOpen`…). This is the backbone of extensibility; build it in Phase 0 so every later module fires hooks.

**API** — external REST/JSON API (parity with WHMCS's 300+ actions) + internal `localAPI()`, scoped **API credentials/roles**, webhooks, **SSO/one-click-login tokens** (mint a short-lived token to drop a client or admin straight into an authenticated session — used for embeds, support handoffs, and control-panel SSO). **[E1, E5]**

### 4.2 Order Form / Cart (Nexus-style)

**Two different "addon" concepts — don't conflate them:** a **product Addon** is a recurring add-on service attached to a client's service (e.g. extra backup space, dedicated IP) — it's billing/provisioning data, sold in the cart. An **AddonModule** (§3) is an installable admin-area plugin/app (e.g. a custom reporting tool) — it's code, activated in Setup → Addons. Same word, unrelated concepts in real WHMCS; keep the data model and the module system for these fully separate.

**Configurable Option Groups** deserve their own spec, not just a passing mention — they're one of WHMCS's fiddliest data/UI areas: option groups shared across products, per-option pricing that varies by billing cycle, quantity-based options (e.g. "extra IPs: $2/each"), hidden/internal-only options, and how option selections feed into upgrade-path proration. Budget this as its own small sub-project inside R4, not a side effect of the product schema.

**Product stock/quantity limits** — oversell protection (a product or configurable option can have a finite stock count that decrements on order and blocks checkout at zero) — add this to the product setup fields; it's easy to miss if products are modeled as unlimited by default.

### 4.4 The Engines (the hard 70% — build these as robust services)

**Billing engine [E2]** — recurring generation ahead of due date, setup fees, first-payment vs recurring pricing, multi-cycle (monthly→triennial), late fees, account credit, partial payments, subscriptions, credit/debit notes, multi-currency with exchange rates, dunning. *This is the single most edge-case-heavy component — treat mixed-cycle + credit + tax ordering as its own hardened sub-project with a big test suite.*

**Upgrade/Downgrade engine [E2]** — its own named workflow, not a sub-clause of billing: change product/configurable-options/cycle mid-term, with an explicit **proration mode matrix** (none / full-credit / prorata-days-remaining), immediate vs next-invoice application, and how it interacts with configurable-option quantity changes. This is one of the highest-bug-risk flows in real WHMCS precisely because it sits at the intersection of billing, products, and provisioning — give it its own test suite alongside the billing engine's.

**Tax/VAT engine** — multi-jurisdiction rate rules (country + state/province level), tax-inclusive vs tax-exclusive product pricing, **VAT number validation** (format + live lookup, e.g. VIES-style) with reverse-charge/exemption handling, per-client tax-exempt flag, tax reporting feed for §4.3 Reports. Called out separately from the billing engine because "compliance-grade multi-level tax" is its own edge-case surface, not a line item inside proration logic.

**Provisioning engine [E1, E2]** — via `ProvisioningModule`s: auto create → suspend → unsuspend → terminate, password/package sync, config push, SSO to control panel, usage-stats pull, **server groups + load balancing**, overage handling.

**Domain engine** — via `RegistrarModule`s: register/transfer/renew, nameserver/contact/lock sync, ID protection, EPP, expiry+status sync, DNS management, grace/redemption handling, TLD pricing import.

**Payment engine [E1]** — `GatewayModule`s (merchant tokenized + third-party redirect), IPN/callback handling, tokenized recurring capture, subscription mgmt, refunds, retries/dunning; ship 2–3 gateways first (Stripe-style dynamic + Paystack/Flutterwave for your NG market + one manual). *Note: PCI scope — tokenize, never store PANs.*

**Support ticketing engine [E4]** — IMAP/POP email piping, department routing, auto-responder, auto-close on inactivity, escalation rules, SLA priority, satisfaction ratings, KB deflection, **AI reply drafting + PII redaction**.

**Fraud engine [E1, E4]** — MaxMind minFraud + custom rules + **AI triage**, order hold/review queue.

**Affiliate engine** — referral tracking, commission accrual, tiers, payout requests.

**Marketing/automation** — mass-mail, lifecycle/rule-based emails, campaign tracking (ties to your CodeVault email-marketing platform). **[E3]**
  - **R11 status:** mass-mail campaigns shipped (`core/Marketing/`) — admin composes subject/HTML body, targets one client group or all active clients, sends through the existing async-email pipeline, and gets a unique open-tracking pixel per recipient. Lifecycle email is scoped to one real, cron-driven case: a service-renewal reminder 7 days ahead of `next_due_date`, reminded at most once per cycle (`RenewalReminderJob`). Cart-abandonment email was considered and deliberately not built — carts are ephemeral session data with no persisted timestamp a cron sweep could find, so it would need a schema change (a persisted cart with a created_at) to do honestly rather than as a stub. Invoice-overdue reminders are the pre-existing R5 `DunningJob`, not duplicated here.

**MarketConnect-style upsell** — resell SSL, email, security addons in-cart.

**Data retention/GDPR** — pruning automation, export/erase requests.

**Migration/Import engine** — general CSV/JSON importer for clients, services, invoices, and transactions (mirrors WHMCS's ImportAssist). Scoped as a generic importer, not a WHMCS-native DB migrator, since there's no live WHMCS instance to migrate *from* here (see §0) — if a real cutover from another billing system happens later, a source-specific adapter can be added on top of this same engine without redesigning it.

### 4.5 Platform-wide systems
Localization (multi-language client+admin, RTL, per-language overrides), multi-currency, PDF engine (invoices/quotes/credit notes), notification providers (Slack/webhook), audit/activity logging, theme system, backup hooks.

- **R11 status:**
  - **Multi-currency** — the R5 stub (schema + one seeded default currency, no conversion wired) is now real: admin Currencies CRUD, a client-facing switcher (session for guests, saved to profile once logged in), and the rate is *locked* onto the order/invoice at checkout — a historical document never re-prices when you later update a rate. Scope boundary: admin screens (invoice list, reports) stay in base currency by design; only client-facing checkout/cart/invoice views convert.
  - **Localization** — `core/Localization/` (LocalizationService + file catalogs in `resources/lang/` overlaid with DB-editable overrides), English/Spanish/Arabic seeded, RTL flips `<html dir>` + loads `rtl.css`. Scope boundary: string coverage is the storefront + cart/checkout + shared header/footer chrome, not the entire admin/client surface — see the README's localization note.
  - **PDF engine** — a hand-rolled `core/Pdf/PdfDocument.php` (zero dependencies, consistent with the rest of the codebase), wired to real invoice PDFs (`/client/invoices/{id}/pdf`, admin equivalent). Validated against poppler's `pdftotext` (an independent real-world parser), not just "the code ran." Quotes and credit notes are **not** separate entities in this build — WHMCS parity here means the PDF *engine* is generic/reusable, but only Invoices exist as a modeled entity to point it at (Quotes/Credit-Notes would each be a new billing entity, out of scope for a PDF task).
  - **Notification providers** — `core/Notifications/`, Slack incoming-webhook + generic HMAC-signed webhook, admin-configurable per hook point. Wired to 4 real events (order placed, invoice paid, new ticket, order fraud-flagged — the last one required adding a `hooks->fire()` call to `FraudService` itself, since that hook point existed in the catalog but was never actually fired before). Live-verified against a real local HTTP receiver, including independently recomputing the HMAC signature to confirm it's correct.
  - **Theme system** — brand name/logo/primary color (`core/Theme/ThemeSettings.php`, backed by the existing settings key-value store), applied to both client area and admin panel via a small addition to `View::render()` (auto-injects resolved theme data the same way it already auto-injects `$view`).
  - **Backup hooks** — admin-triggered + daily-cron backups (`core/Backup/`), wrapping the R1 `BackupManager` (pure-PHP DB dump + file zip, built for pre-OTA-update snapshots) with a tracked history table. Live-testing this surfaced a real, previously-undetected bug in that R1 code: `dumpDatabase()` used `array_column($rows, 0)` against `SHOW TABLES`' associative (`FETCH_ASSOC`) rows, which silently produced an empty dump (just the header comment, no tables) — fixed to `array_map('current', $rows)`, confirmed against a real 60-table dump, and covered by a regression test asserting actual `CREATE TABLE`/`INSERT INTO` content, not just "a file exists."
  - **Security hardening pass** (not itself a §4.5 bullet, but shipped alongside these): standard security headers on every response including a CSP with `script-src 'self'` and no `unsafe-inline` (every inline `onclick`/`onchange`/`onsubmit` in the view layer was moved to `public/assets/js/app.js`'s event-delegation listeners specifically to make that possible); session cookies got `HttpOnly` + `SameSite=Lax` (previously neither was set); `display_errors` is now off outside `APP_ENV=local` (previously full stack traces + filesystem paths leaked to any visitor who triggered a PHP error, in any environment). A full CSRF-token system across all POST forms was scoped out as higher-risk/lower-priority than these (SameSite=Lax already blocks the primary vector) and flagged as a follow-up rather than attempted as a partial, risky sweep.
  - **Load-test pass** surfaced a real correctness bug, not just performance numbers: `CheckoutService` never checked `ProductRepository::decrementStock()`'s return value, so a lost race for the last unit of limited stock (two concurrent checkouts both passing the pre-transaction stock check before either decremented) would silently oversell — the client would be charged for a unit that no longer existed. Fixed by checking the atomic decrement's result inside the order transaction and rolling back with a clean "just sold out" error if it fails. A true race can't be driven deterministically from `php -S` (single-threaded — it happens to serialize the two requests, accidentally masking the bug), so the regression test exercises the exact same code path directly (via reflection + a manually-staled `$priced` snapshot) rather than relying on real concurrency; it was verified to fail against the pre-fix code and pass against the fix. Separately, `php -S`'s single-worker nature was confirmed to correctly serialize/queue concurrent requests without corrupting responses (20 concurrent requests, all 200s, all identical byte-for-byte) — real production concurrency (PHP-FPM with multiple workers) is not something this dev environment can measure.

## 5. Enhancement layer (your doc-2 requirements, applied across the whole platform)

- **BruteGuard security core [E1]** — the full spec from your doc: username-track + IP-track, non-existent-user → immediate IP block, valid-user max-fails → account lock, per-IP thresholds → firewall-tier blocks (1 day/week/month/year), auto-whitelist after 5 clean sessions (green **King** badge), MaxMind country rules (all countries listed: Whitelisted/Not Specified/Blacklisted), manual IP/Country/User controls, retained failed-login history (5/10/15/60 min), full notification set, per-user login-notify toggle, live log panel. Two-layer blocking (app-level Redis gate + optional CSF/nginx sync worker so `exec` stays disabled).
- **Licensed installer [E1]** — **port, don't rebuild from scratch:** `func/bc-levelup.php` + `bc-connect.php` in `DGV7.0 SAAS and NON-SAAS and LM\DGV7.11` already implement almost exactly this — AES-encrypted activation token, domain-binding, remote validation against `manager.pmhserver.name.ng`, a 6h local validation cache, a 48h soft-grace window on API outage, and a `.license.lock` kill-switch. Adapt that logic into WHMP's own `core/`, innocuously named, split across bootstrap/cron/installer. Since WHMP is **internal-only** (not sold/licensed to other companies), scope it down to single-domain self-integrity/anti-tamper — one activation record bound to PhilMoreHost's own domain — not the full multi-license/domain-count enforcement DGV needs for selling to vendors. ionCube encoding + pinned-key signature verification are optional later hardening on top of this, not a v1 requirement.
- **OTA update system [E1, E2]** — also ported from an existing design (`DGV7.0 SAAS and NON-SAAS and LM\update-guide.md`), surfaced in admin Utilities → "Update System": central update feed serves a versioned ZIP + `manifest.json` (new/changed files, an explicit `files_to_delete` list, and DB migration queries) from a non-public-root folder on the LM; the installed side downloads, verifies a **SHA256 checksum**, takes a **pre-update DB+file backup**, extracts to a staging dir (never straight over live files), runs the manifest, and **automatically rolls back** to the backup on any failure. Old-version → new-version + changelog UI with a progress bar, matching the existing DGV design.
- **SEO/AI visibility [E3]** — canonical + JSON-LD (Article/Breadcrumb/Product/Organization) on relevant pages (KB, announcements, store, blog), sitemap automation, `goalzaza-robots.txt`, alt-text enforcement, related-links, About/Author E-E-A-T pages, AI-visibility scorer against the webaloha rubric.
- **Async email [E2]** — Redis queue + worker + editable templates + full event wiring + per-user prefs + email log (mirrors "My Emails").
- **Performance/scale [E2]** — OPcache, Redis sessions/cache, IP-hash or shared-session load balancing, WebP, deferred JS, caching headers, Lighthouse 100 target.
  - **R10 status:** app-level `Cache` interface shipped (`core/Cache/`) — Redis-backed with an in-process array fallback, same resilience pattern as sessions/queue. Wraps the two genuinely expensive public reads (store listing, KB listing), which were also fixed from N+1 (one query per group/category) to a single grouped query each. `sitemap.xml`/`robots.txt` get `Cache-Control` headers. No external JS bundle exists yet to defer — the design system ships CSS only, plus a couple of small inline `<script>` blocks tied to specific DOM elements, where `defer` has no effect. Redis itself couldn't be live-verified in this dev environment (`ext-redis` isn't compiled into this box's PHP build — the array fallback is what actually ran here); the fallback path is unit-tested and the code is spec-correct for a Redis-enabled box. OPcache tuning and IP-hash/shared-session load balancing are server/infra config, not app code — set `opcache.enable=1`, `opcache.validate_timestamps=0` (cache invalidated by deploy, not file mtime, in production), and a shared Redis instance for sessions across app servers when scaling horizontally. A real Lighthouse 100 pass needs a live browser audit — see R10's manual audit task.
- **AI assistant [E4]** — DeepSeek/Claude widget across admin + support + KB search + fraud triage.

## 6. Data model scope

Full WHMCS-equivalent schema — the big table groups: clients/contacts, admins/roles/permissions, products/groups/addons/bundles/configurable-options, orders/order-items, services (hosting accounts), domains, invoices/invoice-items, transactions, credit/quotes/billable-items, tickets/departments/replies/escalations, KB/downloads/announcements/network-issues, servers/server-groups, registrars/gateways/modules config, currencies/tax-rules, promotions, affiliates, email-templates/queue/log, custom-fields, activity/audit logs, **plus** all `security_*` tables from BruteGuard and SEO/media tables. Every table: FKs, indexes on lookup columns, timestamps, reversible soft-delete where it matters.

**Single-tenant, no `tenant_id` sprawl.** Since WHMP is internal-only (§10), the schema is plain single-tenant like a real WHMCS install — no tenant scoping column threaded through every table. The one license/activation table is small and modeled on the DGV7.11 pattern (key, bound domain, validation cache, last-checked timestamp) — not DGV's full multi-license schema (`licenses`/`licensed_domains`/`download_tokens`) that exists to sell per-domain licenses to vendors. If WHMP is ever productized later, keep the activation logic behind one small interface so that path doesn't force a schema rewrite.

## 7. Module/hook/API contracts to lock early

Because everything plugs into them, these get designed in Phase 0–1 and frozen:
1. Module base contracts (Provisioning/Registrar/Gateway/Addon/Report/Notification/Widget).
2. Hook dispatcher + the initial hook-point catalog.
3. API request/auth/response envelope + credential/role model.
4. The design-system component library.

Get these right and later phases parallelize cleanly. Change them late and everything downstream churns.

### 7.1 Testing & parity-verification strategy

There is no live WHMCS instance anywhere in this environment to diff behavior against (§0) — so "does this match WHMCS" can't be answered by running both systems side by side. Verification instead relies on a **hand-authored PHPUnit test matrix** built from documented/known WHMCS billing rules: rounding behavior, cycle-change proration modes (none/full/prorata — §4.4), tax-inclusive vs exclusive pricing, mixed-currency invoicing, and credit-application order. Treat this matrix as a first-class deliverable of R5 (billing engine), not an afterthought — it's the highest-risk area for silent, financially-impactful bugs, and it should be reviewed by you specifically before R5 is considered done, not just green-lit by CI.

### 7.2 Non-goals

Bounding scope explicitly, so it doesn't creep:
- **Not a control panel.** cPanel/CyberPanel/Plesk/etc. stay external systems — WHMP only *integrates* with them via `ProvisioningModule`s (§3). It never reimplements panel functionality.
- **Not a website builder or general CMS.** That's CodeVault's job, a fully separate product with its own codebase and database — WHMP has no page-builder, no blog/forum engine of its own beyond the WHMCS-parity Knowledgebase/Announcements/Downloads pages already in §4.1.
- **Not a DNS server.** The domain engine (§4.4) integrates with existing DNS infrastructure via `RegistrarModule`s/DNS APIs; it doesn't run authoritative DNS itself.

## 8. Phased release roadmap

Sequenced into **usable releases** — each ships something real, not just scaffolding.

**R0 · Foundation** — kernel, module SDK contracts, hook system, API envelope, design system, cron+queue. *(serial; the spine)*

**R1 · Installer + schema + integrity/activation** — 4 stages, full DDL, config lock, **port the DGV7.11 licensing pattern (`bc-levelup.php`/`bc-connect.php`) + build the OTA update system** (both per §5) rather than designing activation from zero. *(gate)*

**R2 · Auth + BruteGuard security core** — full anti-brute-force per doc 2. *(highest-risk; heavy tests)*

**R3 · Clients + Admin shell + Staff/roles** — client CRUD, admin dashboard, permission matrix, custom fields, email templates + async email.

**R4 · Products + Order/Cart + Payment engine (2–3 gateways)** — catalogue, configurable options, cart, checkout, invoicing basics. *(first revenue-capable release)*

**R5 · Billing engine (full)** — recurring, proration, mixed cycles, tax/VAT, credit, refunds, dunning, credit/debit notes, multi-currency. *(the hard one — own test suite)*

**R6 · Provisioning engine + first server modules (cPanel + CyberPanel)** — create/suspend/terminate/SSO/usage, server groups.

**R7 · Domain engine + registrar modules + DNS mgmt** — register/transfer/renew/sync, ID protection, EPP.

**R8 · Support ticketing + KB/Downloads/Announcements + AI Copilot** — email piping, departments, escalation, AI drafting.

**R9 · Fraud + Affiliates + Reports + MarketConnect-style upsell.**

With the site able to reach the installer for the first time, the user supplied the *original* 4-stage installer spec verbatim and asked for it to be verified against the real implementation before trusting it in production. A second research subagent audited all 4 stages point-by-point and found five real deviations: (1) Stage 1 had PHP-version/extension checks but no "Welcome" branding and no license-key field — the field lived on Stage 4 instead; (2) the license validation endpoint didn't match what the user specified (`/api-docs.php` vs. the code's `/api.php` — user confirmed keep `/api.php`, since `/api-docs.php` reads as a documentation page, not a POST-able endpoint); (3) **the license system was not obfuscated at all** — `core/Licensing/LicenseManager.php` and five sibling files sat in plain sight with "license" in every class name, the namespace, a DB table (`license_activation`), and storage paths, directly contradicting the stated "should not even be mentioned" requirement; (4) Stage 3's admin-creation `INSERT` never set `role_id` — migration 0013's backfill query (`UPDATE admins SET role_id = ... WHERE role_id IS NULL`) runs during Stage 2, before any admin exists on a fresh install, so it backfills zero rows and the installer's own bootstrap admin was left roleless, meaning `AuthGuard::can()` (which hard-denies on `role_id === null`) would have silently locked the first admin out of every permission check immediately after setup; (5) Stage 4 was a generic "Setup complete" card that even leaked an internal dev note ("Admin login lands with R2...") rather than the requested congratulations/instructions page.

Fixed all five. Renamed `core/Licensing/` → `core/Integrity/` (`LicenseManager`→`IntegrityManager`, `LicenseHttpClient`→`IntegrityHttpClient`, `CurlLicenseHttpClient`→`CurlIntegrityHttpClient`, `LicenseStatus`→`IntegrityStatus`, `LicenseTokenCipher`→`IntegrityTokenCipher`, `LicenseCheckJob`→`IntegrityCheckJob`, methods `storeLicenseKey()`/`licenseKey()`→`storeActivationKey()`/`activationKey()`), renamed the `storage/license/` directory and `.license.lock` kill-switch to `storage/system/`/`.integrity.lock`, and renamed the `license_activation` table to `system_activation` — via a **new, additive** migration (`RENAME TABLE`) rather than editing migration 0003, which stays untouched exactly as already-applied on every existing install; the rename is a second migration on top of it. Also renamed the `license_key`/`activation_key` HTTP form field, since a raw view-source of the install page is exactly the kind of "easy tracing" the requirement was guarding against. Merged Stage 1's requirements-check view with new welcome copy and the (moved) activation-key form; Stage 3's `admin()` now explicitly looks up `SELECT id FROM roles WHERE is_super_admin = 1` and includes it in the `INSERT`, rather than depending on a backfill that structurally can never reach a not-yet-created row; Stage 4 (`install.done`) is now a real "Congratulations" page with a numbered next-steps list (payment gateways, servers/domains, settings, cron) and links to log in.

While live-testing the rewritten flow end-to-end, found a sixth issue — not on the original checklist, self-discovered, and the most serious of the six: **every installer stage remained fully reachable and fully functional after `.installed.lock` already existed.** Proven by actually exploiting it in an isolated scratch copy: with a completed install in place, `POST /install/admin` still created a second admin account with attacker-chosen credentials and no authentication required. `needsInstallRedirect()` (the site-wide gate) was never meant to guard against this — it only controls whether *other* routes get bounced to `/install`, and deliberately lets `/install/*` itself through unconditionally so the wizard can run *during* setup; nothing inside `InstallController` itself checked whether setup had already finished. Fixed with a new `refuseIfAlreadyInstalled()` guard (redirects to `/` if `.installed.lock` exists) added to the top of `requirements()`, `database()`, and `admin()` — deliberately *not* added to `finish()`, since that's the method that creates the lock file on the one legitimate call where it doesn't yet exist; re-visits after that are already harmless no-ops (the existing `is_file()` check skips re-writing the lock, and the page it re-renders leaks nothing sensitive).

Every piece was live-verified against a real, fully isolated environment — not just unit tests — because this was about to go live: created a full scratch copy of the project (excluded from the real local dev environment's `.installed.lock`/`.env` so nothing about the actual working setup was touched), a disposable scratch MySQL database, and a dedicated PHP dev server on its own port. Walked all 4 real HTTP stages in sequence with cookie-jar sessions: Stage 1 correctly showed "Welcome" + all requirements passing + the activation-key field and correctly redirected once submitted; Stage 2 connected to the real scratch database and ran all 95 real migrations, confirmed via direct SQL that `system_activation` (not `license_activation`) existed; Stage 3 created a real admin account and confirmed via direct SQL that `role_id = 1` was set (the bug fix, proven, not assumed); Stage 4 showed the real congratulations copy and wrote `.installed.lock`; the activation key from Stage 1 was confirmed present on disk in encrypted (non-plaintext) form. Then logged in as that installer-created admin through the real `/login` flow and confirmed a permission-gated screen (`/admin/staff`) returned 200, not 403 — proving the `role_id` fix actually translates into working access, not just a non-null database column. Finally, proved the pre-fix vulnerability was real by exploiting it (a second admin account was successfully created post-lock against the unpatched code), then re-ran the identical exploit attempt against the patched code and confirmed it correctly redirected away with zero rows added. The scratch database, scratch server, and scratch project copy were all torn down afterward. No new PHPUnit tests were added for `InstallController` specifically (no dedicated test file existed before this round either, and its constructor pulls in the full `Kernel` — live HTTP verification against an isolated real environment was the more meaningful check for an installer, consistent with how R30's admin-controller fix was verified). Full suite re-run clean after the rename.

**R24 · NotificationModule SDK — fixing a real architectural inconsistency, not filling another empty stub.** A gap survey this round checked something none of R20-R23's surveys had verified precisely: whether `ReportModule`/`SecurityQuestionModule` were really still the *only* ghost Module SDK interfaces, as R21's status log had claimed. They weren't — `core/Modules/NotificationModule.php` was a third one, registered in `ModuleManager::TYPES` since R0 but with zero implementers, while R11's *real* Slack/webhook notification delivery had been built entirely against a separate, parallel `core/Notifications/NotificationProvider.php` interface that has nothing to do with the Module SDK. This wasn't a missing feature (like R20/R21's addon/widget gaps) or a missing feature-area (like R22's VAT work, R23's Quotes) — it was two disconnected systems doing overlapping jobs, a genuine architectural inconsistency worth fixing directly rather than a third "activation lifecycle" exercise. The fix: redefined `NotificationModule` as `extends Module, NotificationProvider` — a module *is* a provider (same `send(url, secret, message, context): bool` shape Slack/Webhook already implement correctly) plus the SDK's `metadata()`/`configOptions()` for admin discoverability, rather than inventing a second incompatible contract. `NotificationDispatcher` now resolves any `notification_endpoints` row whose `type` isn't one of the two built-ins (`slack`/`webhook`) by looking up a registered `NotificationModule` with that slug — the endpoint's own `type` column doubles as the module slug, so no new column or table was needed, just widening `type` from a hard `ENUM('slack','webhook')` to `VARCHAR(32)` so a third-party module's slug is a valid value without a migration every time one ships. An unregistered/removed module type is skipped silently (same fail-open posture as a Slack outage), never an error. Shipped one real built-in implementer, `DiscordNotificationModule` — posts to a Discord incoming-webhook URL (`{"content": "..."}`, the same no-bot-token shape `SlackNotificationProvider` already uses for Slack) — and extended the admin endpoint form's Type dropdown to list every registered `NotificationModule` alongside the two built-ins, computed dynamically via `ModuleManager::allOfType()` rather than hardcoded, so a future fourth module needs zero controller/view changes to become selectable.

Live-verified against the running dev app with a disposable admin account (cleaned up afterward): confirmed "Discord (module)" appears in the real endpoint-creation dropdown exactly as registered; created a real Discord-type endpoint through the actual admin form and confirmed it lists correctly; then — rather than only asserting this through a unit test — constructed `NotificationDispatcher` through the *exact* `Kernel`-wired container (same DI graph a real request uses) and called `dispatch('OrderPlaced', ...)` directly, confirming it correctly resolved the persisted Discord endpoint to the registered module and attempted a real network POST to the (deliberately fake) webhook URL, completing without throwing — the fail-open contract holding under a genuine network failure, not just a mocked one; confirmed toggle-active and the permission gate both still work unchanged. Backed by 8 new/updated PHPUnit tests in `NotificationDispatcherTest` (module-slug resolution, unregistered-type skip, `DiscordNotificationModule` metadata/payload/status-code handling) plus the pre-existing Slack/webhook coverage re-verified passing against the new 4-argument `NotificationDispatcher` constructor. Full suite, 0 regressions.
